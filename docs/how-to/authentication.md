# Authentication and secret rotation

API deployments require authentication. Query API tokens use `?access_token=...`. Basic uses a username/password pair. Bearer tokens are signed JWTs verified against the configured issuer, audience and JWKS URI; an opaque API token is not a bearer JWT.

Configure `spec.auth.tokenSecret` with a Secret containing `token`, or let the operator generate one. `spec.auth.basicSecret` refers to a Secret with `username` and `password`. Supply credentials through your secret-management system. Use HTTPS; configure ingress access logging to omit query strings because the TADS query authentication mechanism puts credentials in the URL.

OAuth2 settings live under `spec.auth.oauth2`: `issuer`, `audience`, `jwksURI`, optional `algorithms` and scope names. Defaults are `tads-api/read`, `tads-api/write`, `tads-api/delete`, and `tads-api/admin`. The CRD requires issuer, audience and JWKS URI together, nonempty HTTPS URLs, and supported asymmetric algorithms. The controller validates URL hosts and rejects embedded credentials. The standalone runtime permits HTTP only in development mode. JWT verification fails closed when keys or claims cannot be verified. The verifier caches JWKS for five minutes and limits unknown-key refreshes to once per 30 seconds. Publish new signing keys before issuing tokens that use them; known cached keys remain usable during a brief JWKS outage. The operator supplies API authentication credentials only to API pods; workers and schema Jobs do not receive them.

Update the referenced Secret and wait for `task env:wait`. The operator fingerprints the kind, namespace, name, UID and resourceVersion of referenced Secret and CA objects. It never hashes credential bytes into annotations or schema Job names. Object metadata edits also cause rollouts; database and CA revisions rerun the idempotent schema Job. During rollout both credentials can be accepted by different pods; verify old credentials are rejected after every replica has updated. Never put credentials in a CR, issue, test report or support bundle.

Webhook subscriptions belong to the authenticated subject; administrators may manage all subscriptions. Delivery secrets are write-only and preserved when omitted from updates. URL or filter changes invalidate queued deliveries. Tags, authentication header names, delivery secrets and reasserting an active status preserve the backlog. Disabling and re-enabling increments the revision so old jobs cannot revive. Filter array order does not matter; an absent filter differs from an empty list. GET responses, including server-owned error details, can be PUT back with `status: created` to re-enable a subscription; the server discards the old error. If credentials rotate during a failed send, that job retries the current credentials with a fresh attempt budget. Delivery is at least once: consumers must tolerate retries. Redirects and private, loopback, link-local and metadata destinations are denied unless an explicit host exception permits a private destination; metadata endpoints remain denied. DNS addresses are checked at delivery and the connection is pinned to the checked address.

Webhook retries use `TADOSS_WEBHOOK_MAX_ATTEMPTS`. Expected transport errors, including malformed HTTP, and unexpected sender failures update the fenced job and subscription together. Logs contain exception classes, job identifiers and SQLSTATE where available, without receiver bytes, exception messages or credentials. See [worker limits](../reference/configuration.md#database-tls-and-worker-limits) for deadline and DNS behavior.
